# EVENT_ARCHITECTURE.md

## Purpose

This document defines the Event Architecture of AcCore.

Event Architecture provides a standardized mechanism for publishing, transporting, and consuming business facts generated by the platform.

The architecture supports integrations, notifications, synchronization, workflows, and platform extensibility while preserving the deterministic execution model of the accounting core.

Event Architecture is an extension mechanism.

Event Architecture is not a business execution mechanism.

---

# Architectural Position

Event Architecture operates alongside the core business execution pipeline.

```text
Business Objects
        ↓
Posting
        ↓
Registers
        ↓
Valuation
        ↓
Reporting
        ↓
Business Facts
        ↓
Event Architecture
```

Business execution does not depend on event processing.

Events are generated from completed business facts.

---

# Event-Aware Principle

AcCore follows an Event-Aware Architecture.

Events are used to:

* Observe business activity
* Publish business facts
* Integrate external systems
* Trigger notifications
* Enable workflow extensions
* Support synchronization

Events are not used to drive core accounting execution.

---

# Event Definition

## Event

An Event is an immutable representation of a completed business fact.

Events describe:

```text
What happened
```

Events do not describe:

```text
What should happen
```

---

## Examples

Valid events:

```text
CustomerCreated

DocumentPosted

InventoryChanged

CostRecalculated

DatasetGenerated
```

Invalid events:

```text
CreateCustomer

PostDocument

CalculateCost
```

These represent commands rather than facts.

---

# Event Characteristics

Events are:

* Immutable
* Historical
* Observable
* Publishable
* Versionable

Once published, an event cannot be modified.

---

# Event Lifecycle

Events follow a standardized lifecycle.

```text
Business Fact
        ↓
Event Creation
        ↓
Event Publication
        ↓
Event Delivery
        ↓
Subscriber Processing
```

Each stage is independent and observable.

---

# Transaction Boundary

Business transactions complete before event publication begins.

```text
Business Operation
        ↓
Transaction Commit
        ↓
Event Publication
```

Subscribers always observe committed facts.

---

# Event Publication Model

Business subsystems publish events through a unified publication mechanism.

```text
Business Subsystem
        ↓
Event Publisher
        ↓
Event Runtime
```

Subsystems do not communicate directly with subscribers.

---

# Event Publisher

## Purpose

The Event Publisher is responsible for submitting events into the Event Runtime.

---

## Responsibilities

* Event creation
* Event validation
* Event submission
* Event metadata attachment

The publisher does not perform delivery.

---

# Event Runtime

## Purpose

The Event Runtime manages event processing and distribution.

---

## Responsibilities

* Event registration
* Event routing
* Subscriber discovery
* Event dispatching
* Event filtering
* Delivery coordination

---

## Architecture

```text
Event Publisher
        ↓
Event Runtime
        ↓
Subscribers
```

The Event Runtime is the central event coordination component.

---

# Event Manager

The Event Manager is the primary runtime entry point for event operations.

Typical responsibilities include:

* Publish
* Subscribe
* Unsubscribe
* Dispatch
* Monitor

The Event Manager operates independently from business subsystems.

---

# Subscriber Model

Subscribers consume published events.

---

## Examples

```text
CRM Connector

Email Service

Workflow Engine

Mobile Synchronization Service

External ERP Connector
```

---

## Subscriber Characteristics

Subscribers:

* Are independent
* Are replaceable
* May be added without modifying publishers
* May be removed without modifying publishers

---

# Publisher Subscriber Independence

Publishers remain unaware of subscribers.

Subscribers remain unaware of publishers.

Communication occurs exclusively through Event Contracts and Event Runtime.

---

# Event Contracts

All externally visible events are defined through Event Contracts.

---

## Purpose

Event Contracts define:

* Event structure
* Event schema
* Event version
* Event metadata

---

## Example

```text
DocumentPostedEventContract
```

---

## Benefits

* Stable interfaces
* Versioning support
* Consumer compatibility
* Protocol independence

---

# Event Metadata Model

Events are metadata-defined platform objects.

Examples:

```text
EventDefinition

EventContractDefinition

SubscriberDefinition
```

---

## Metadata Lifecycle

```text
Metadata
        ↓
Compiler
        ↓
Runtime Event Objects
```

The Event Architecture follows the platform-wide Metadata → Compilation → Runtime model.

---

# Event Versioning

Events are versioned integration artifacts.

Versioning applies to Event Contracts.

Example:

```text
DocumentPostedEvent v1

DocumentPostedEvent v2
```

Versioning supports:

* Backward compatibility
* Evolution of event schemas
* Consumer stability

---

# Event Filtering

Subscribers may define event filters.

Examples:

```text
Only Inventory Events

Only Cost Events

Only Customer Events
```

Filtering occurs within Event Runtime.

Publishers remain unaffected.

---

# Event Delivery Model

Event delivery is managed by Event Runtime.

The architecture supports:

* Immediate delivery
* Deferred delivery
* Batch delivery

Delivery strategy remains independent from business logic.

---

# Runtime Integration

Event Architecture integrates with all major runtime subsystems.

```text
Business Objects
Posting
Registers
Valuation
Reporting
        ↓
Business Facts
        ↓
Event Runtime
```

Event processing never bypasses runtime boundaries.

# ADR-028: AcCore Is Event-Aware

## Status

Accepted

## Decision

AcCore uses events as a mechanism for observation, integration, notification, and extension.

Events do not drive core business execution.

## Consequences

* Deterministic business execution.
* Stable accounting behavior.
* Event processing remains optional.
* Integration extensibility is preserved.

---

# ADR-029: Events Are Published After Transaction Completion

## Status

Accepted

## Decision

Events are published only after successful completion of the originating business transaction.

## Consequences

* Events represent committed facts.
* Failed operations produce no events.
* Event failures do not rollback business transactions.

---

# ADR-030: Publishers Are Independent From Subscribers

## Status

Accepted

## Decision

Event publishers remain unaware of subscriber implementations.

## Consequences

* Loose coupling.
* Independent evolution.
* Easier extensibility.
* Simplified maintenance.

---

# ADR-031: Events Are Contract-Based

## Status

Accepted

## Decision

Published events are defined through Event Contracts.

## Consequences

* Versioning support.
* Consumer stability.
* Consistent integration model.
* Protocol independence.

---

# Architectural Summary

Event Architecture provides a standardized, contract-based, event-aware mechanism for publishing business facts generated by AcCore.

The architecture enables integrations, notifications, synchronization, and future workflow automation while preserving the deterministic execution model of the accounting core.

Events extend the platform.

Events do not drive the platform.
