# POSTING_EVENTS.md

## 1. Purpose

This document defines posting-related events generated by the Posting Architecture.

Events communicate successful posting state changes to other platform subsystems.

---

## 2. Architectural Principles

### 2.1 Event-Driven Integration

Subsystems should react to posting events instead of directly coupling to Posting Engine internals.

---

### 2.2 Post-Commit Publication

Events are published only after successful transaction commit.

---

### 2.3 Immutable Event Data

Published events are immutable.

---

## 3. Event Model

An event represents a completed posting-related action.

Conceptually:

Event

* event_id
* timestamp
* event_type
* object_id
* payload

---

## 4. Core Events

### 4.1 DocumentPosted

Generated after successful posting.

Payload may include:

* document_id
* document_type
* posting_timestamp

---

### 4.2 DocumentUnposted

Generated after successful unposting.

---

### 4.3 DocumentReposted

Generated after successful reposting.

---

### 4.4 DocumentMarkedDirty

Generated when consistency tracking marks an object as DIRTY.

---

### 4.5 ConsistencyRestored

Generated after successful consistency restoration.

---

## 5. Event Consumers

Potential consumers:

* dependency subsystem;
* notification subsystem;
* audit subsystem;
* integration subsystem;
* background processing subsystem.

---

## 6. Event Ordering

Events originating from the same posting transaction must preserve execution order.

---

## 7. Delivery Guarantees

The platform should guarantee that committed posting operations produce corresponding events.

The exact delivery mechanism is implementation-specific.

---

## 8. Future Events

Future versions may introduce:

* TotalsUpdated
* DependencyDetected
* RegisterChanged
* PeriodClosed
