# Phase 6 — Step 4

# Register Movement Contract

## 1. Purpose

This document defines the semantic contract between the Posting Architecture and Register Architecture.

The purpose of this step is to formally define what a `Movement` means, what information a Movement must contain, which responsibilities belong to Posting, which responsibilities belong to Register Architecture, and where Register Posting Contracts participate in movement acceptance.

This document defines the semantic contract only.

It does not define a concrete Python class, persistence representation, database schema, movement service API, transaction API, or register implementation.

The central architectural principle is:

> Posting generates accounting facts. Register Architecture defines whether those facts are acceptable according to the applicable Register Posting Contract.

---

## 2. Relationship with Existing Architecture

Step 4 builds on the Posting Architecture and the semantic contracts established by Steps 1–3.

The existing architecture defines:

```text
Operational Document
        ↓
Posting Engine
        ↓
Posting Context
        ↓
Posting Handler
        ↓
MovementSet
        ↓
Movement Validation
        ↓
Persistence / Application Coordination
        ↓
Logical Completion
        ↓
Posting Events
```

Step 4 defines the semantic meaning and acceptance boundary of the `Movement` objects inside the `MovementSet`.

The resulting relationship is:

```text
Posting Handler
        ↓
MovementSet
        ↓
Movement Validation
        ↓
Register Posting Contract
        ↓
Register Acceptance
        ↓
Required Persistent Result
```

The Register does not own posting semantics.

The Posting Handler does not own Register-specific acceptance rules.

The Register Posting Contract is the boundary between these responsibilities.

---

## 3. Movement Semantic Definition

A `Movement` is a business/accounting fact generated as a result of a Posting operation and intended to be accepted by a specific Register according to that Register's posting contract.

A Movement describes an accounting effect in semantic terms.

Conceptually:

```text
Movement
│
├── movement identity
├── source document identity
├── register identity
├── movement type
├── dimensions
├── resources
├── attributes
└── accounting time
```

This is a conceptual model.

It does not prescribe the concrete representation of these fields.

A Movement is not itself a database row, storage object, or serialization format.

---

## 4. Movement as an Accounting Fact

A Movement represents an accounting fact produced by Posting.

The fact describes what accounting effect the source document produces in the target Register.

The Movement therefore belongs to the semantic accounting layer rather than directly to the physical persistence layer.

The distinction is:

```text
Movement
    ↓
Accounting fact

Persistence representation
    ↓
Physical representation of that fact
```

Therefore:

```text
Movement ≠ Storage Record
```

A persistence implementation may represent a Movement as one or more physical records, but such representation is outside this contract.

The semantic meaning of a Movement must remain independent from its physical storage representation.

---

## 5. Movement Identity

A Movement may have an identity distinct from the identity of its source document.

These identities represent different concepts:

```text
Source Document Identity
    → identifies the business object that caused the accounting effect

Movement Identity
    → identifies the accounting fact itself
```

The existence, generation mechanism, and persistence representation of Movement identity are implementation concerns unless a concrete Register contract requires a durable movement identity.

This step therefore does not prescribe:

* UUIDs;
* database-generated identifiers;
* sequential identifiers;
* hashes;
* composite keys;
* concrete Python identifier types.

Movement identity must not be confused with source document identity.

---

## 6. Source Document Identity

Every Movement generated by Posting must contain an explicit identity of the source document responsible for the accounting effect.

The source identity is a durable semantic reference to the originating business object.

The relationship is:

```text
Runtime Object
      ↓
Object Identity
      ↓
Movement.source_document_identity
```

A runtime object reference is not itself a durable accounting identity.

Therefore a Movement must not depend on:

* Python object identity;
* memory address;
* runtime object reference;
* transient runtime state.

The source document identity allows accounting effects to remain associated with their originating business object independently of the current runtime instance.

This is required for:

* unposting;
* reposting;
* identifying existing accounting effects;
* restoring accounting state;
* auditing;
* persistence;
* dependency integration.

---

## 7. Register Identity

A Movement explicitly identifies the Register for which the accounting fact is intended.

Conceptually:

```text
Movement
    ↓
Register Identity
```

Register identity answers:

> Which Register accepts and interprets this Movement according to its posting contract?

The concrete representation of Register identity is not defined by this step.

It may later be represented through a metadata identity, architectural identifier, or another explicit identity mechanism.

This step does not prescribe the representation.

Posting remains register-agnostic at the orchestration level.

The Posting Engine must not contain register-specific accounting requirements.

---

## 8. Movement Type

A Movement contains a semantic movement type describing the kind of accounting effect represented by the Movement.

Movement type is part of the accounting fact and may participate in Register Posting Contract validation.

The movement type must be interpreted according to the applicable Register semantics.

This step does not define concrete movement type values.

It therefore does not prescribe names such as:

```text
Receipt
Issue
Transfer
Adjustment
```

or any Register-specific subclasses.

The concrete movement type vocabulary belongs to the relevant accounting/register architecture and may be defined in later implementation steps.

---

## 9. Dimensions

Dimensions identify the accounting context in which the Movement applies.

Conceptually:

```text
Dimensions
    → identify the aggregation context of the accounting fact
```

Examples of dimensions may exist in particular Registers, but this step does not prescribe a universal dimension set.

A Register Posting Contract determines which dimensions are:

* required;
* optional;
* allowed;
* type-constrained;
* identity-constrained;
* subject to additional validation.

Dimensions are semantic accounting data.

They must not be treated as an arbitrary persistence field bag.

---

## 10. Resources

Resources carry quantitative or otherwise accumulated accounting values represented by a Movement.

Conceptually:

```text
Resources
    → carry quantitative / accumulated values
```

The concrete resources available to a Movement depend on the applicable Register.

A Register Posting Contract determines which resources are required and what semantic/type constraints apply.

The Movement contract does not prescribe:

* a universal quantity resource;
* a universal monetary resource;
* a concrete numeric type;
* a database column representation;
* a particular unit system.

Resource semantics are defined by the applicable Register architecture.

---

## 11. Attributes

Attributes carry additional descriptive fact data associated with a Movement.

Conceptually:

```text
Attributes
    → carry additional descriptive accounting data
```

Attributes are distinct from dimensions and resources.

They do not automatically participate in aggregation merely because they are present in a Movement.

A Register Posting Contract may define:

* required attributes;
* allowed attributes;
* attribute types;
* identity/reference semantics;
* validation rules.

This step does not prescribe a generic EAV persistence model.

The semantic distinction between dimensions, resources, and attributes must remain independent from their eventual physical representation.

---

## 12. Movement Time

A Movement may contain semantic temporal information required by the applicable accounting model.

Movement time is optional at the universal Movement level.

A Movement MUST NOT be required to contain a specific temporal value unless that requirement is defined by the applicable Register Posting Contract.

If a Register requires a specific accounting date or time, that requirement belongs to the applicable Register Posting Contract.

The universal Movement contract therefore does not prescribe:

* a mandatory timestamp field;
* a mandatory accounting date field;
* a specific time representation;
* a specific timezone model;
* a specific source of current time.

When temporal information is present, its meaning MUST be defined by the applicable accounting semantics and MUST NOT depend on runtime object identity or uncontrolled system time.

Concrete temporal requirements are outside the scope of this step.

---

## 13. MovementSet Relationship

A `MovementSet` is the complete collection of Movements generated by one Posting operation.

The relationship is:

```text
Posting Handler
      ↓
MovementSet
      ↓
Movement Validation
      ↓
Register Acceptance
```

A Movement is one accounting fact within that complete result.

The Movement contract does not redefine the MovementSet contract established by the Posting semantic model.

The following invariant remains in force:

> One Posting operation produces exactly one complete MovementSet.

The MovementSet must be complete before Register acceptance is evaluated.

Register Architecture must not need to infer missing Movements from partial handler output.

---

## 14. Register Posting Contract Boundary

Register-specific requirements are expressed through the Register Posting Contract.

The conceptual relationship is:

```text
Universal Movement
        ↓
Register Posting Contract
        ↓
Register-specific acceptance
```

This preserves the separation between:

* generic Posting infrastructure;
* universal Movement semantics;
* Register-specific accounting requirements.

The Register Posting Contract may define requirements concerning:

* Register identity;
* movement type;
* dimensions;
* resources;
* attributes;
* value types;
* required references;
* allowed combinations;
* additional semantic constraints.

The contract is the authoritative boundary for determining whether a Movement is acceptable for the target Register.

---

## 15. Movement Acceptance

A Register may accept a Movement for Register processing only when the Movement satisfies all applicable requirements.

The acceptance boundary is defined by the applicable Register Posting Contract.

Conceptually:

```text
Movement
    ↓
Movement Validation
    ↓
Register Posting Contract
    ↓
Accepted for Register Processing
    ↓
Persistence / Application Coordination
```

Register acceptance means that the Movement satisfies the semantic requirements necessary for the Register to process the accounting fact.

Register acceptance is NOT equivalent to physical persistence.

An accepted Movement MUST NOT be interpreted as proof that the required persistent accounting result has already been established.

The Posting Engine remains responsible for coordinating the required persistent result after movement validation and Register Contract acceptance.

The Register Posting Contract therefore defines an acceptance boundary, not a physical persistence boundary.

The distinction is:

```text
Accepted Movement
    ≠
Persisted Register Record
```

Physical persistence, transaction mechanisms, storage providers, and commit semantics remain outside the semantic Movement contract.

---

## 16. Movement Validation

Movement Validation is performed before a Movement becomes part of the required persistent accounting result.

The validation boundary remains separate from Posting Handler business logic.

The responsibilities are:

```text
Posting Handler
    → generates Movement

Movement Validator
    → validates Movement

Register Posting Contract
    → defines Register-specific acceptance requirements

Register Architecture
    → applies accepted accounting facts
```

A Movement that fails validation cannot be accepted as a successful accounting effect.

Validation failure therefore propagates to the Posting operation as a Posting failure.

---

## 17. Register Responsibility

The Register is responsible for defining and enforcing the Register-specific requirements applicable to accepted Movements.

Register responsibilities include:

* defining Register-specific movement requirements;
* exposing those requirements through the applicable Register Posting Contract;
* determining whether a Movement satisfies the Register's acceptance conditions;
* interpreting accepted accounting facts according to Register semantics;
* managing the Register's accounting representation;
* maintaining the persistent accounting state required by the Register.

Register acceptance is an architectural boundary between universal Movement semantics and Register-specific accounting semantics.

The Register MUST NOT own document-specific posting logic.

The Register MUST NOT infer arbitrary business semantics from an invalid Movement.

The Register MUST NOT silently repair, reinterpret, or mutate a Movement in order to make an otherwise invalid Movement acceptable.

Acceptance by the Register Posting Contract does not itself establish the required persistent accounting result.

The establishment of the required persistent result is coordinated by the Posting Architecture through the applicable Persistence / Application boundary.

The Register therefore owns Register semantics and acceptance, while Posting owns document-specific accounting semantics and posting orchestration.

---

## 18. Posting Responsibility

Posting Architecture is responsible for producing the accounting facts resulting from a business object's Posting operation.

Posting responsibilities include:

* resolving the applicable Posting Handler;
* providing Posting Context;
* executing the Handler;
* receiving the complete MovementSet;
* coordinating Movement validation;
* coordinating Register acceptance;
* coordinating the required persistent accounting result;
* completing the Posting lifecycle.

Posting does not own Register-specific storage semantics.

Posting must not bypass the Register Posting Contract.

---

## 19. Movement Immutability

Once generated by the Posting Handler, a Movement must not be silently mutated by later layers.

The lifecycle is:

```text
Generated Movement
      ↓
Validated Movement
      ↓
Accepted Movement
      ↓
Applied Accounting Effect
```

A later layer must not silently transform:

```text
invalid Movement
      ↓
repaired Movement
```

in order to make the Movement acceptable.

If a Movement violates an applicable contract, the correct semantic result is validation/acceptance failure.

This preserves the principle:

> Register does not reinterpret or silently repair an invalid Movement.

Any explicit transformation required by a future architecture must be represented as an explicit architectural operation rather than hidden mutation.

---

## 20. Movement Completeness

A Movement must contain sufficient semantic information for the applicable Register Posting Contract to determine whether it can be accepted.

Completeness is evaluated relative to the applicable Register.

Therefore there is no requirement that every Movement contain every possible field.

Instead:

```text
Movement completeness
    =
    sufficient semantic data
    for the applicable Register contract
```

A Movement that omits a required dimension, resource, attribute, identity, or other contract-defined value is incomplete and cannot be accepted.

The Posting Handler is responsible for generating the complete accounting fact.

The Register is responsible for defining what constitutes sufficient information for its acceptance.

---

## 21. Deterministic Movement Generation

For equivalent relevant semantic input state and equivalent applicable Posting Context, Posting must produce semantically equivalent Movement results.

This includes equivalent:

* source document identity;
* Register identity;
* movement types;
* dimensions;
* resources;
* attributes;
* applicable accounting time.

Concrete runtime object identity or physical persistence details must not change the semantic accounting result.

Determinism is required for predictable Posting, validation, testing, and reposting behavior.

The exact deterministic implementation mechanism is outside this step.

---

## 22. Persistence Semantics

A Movement is a semantic accounting fact, not a persistence API.

The persistence lifecycle is therefore:

```text
Movement
      ↓
Validation
      ↓
Register Acceptance
      ↓
Persistence / Application Coordination
      ↓
Required Persistent Accounting Result
```

This step does not prescribe:

* database schema;
* storage provider;
* persistence repository;
* movement service API;
* transaction API;
* serialization format;
* physical record layout.

Those concerns belong to the appropriate Persistence and Register Architecture boundaries.

The Phase 5 storage and persistence boundaries remain unchanged.

## 23. Movement Lifecycle

Movement does not define an independent persistent lifecycle separate from the Posting operation.

The semantic progression relevant to a Movement is:

```text
Generated
    ↓
Validated
    ↓
Accepted for Register Processing
    ↓
Participates in Required Persistent Accounting Result
```

### 23.1 Generated

A Movement is generated by the Posting Handler as part of the complete MovementSet produced by a Posting operation.

At this stage the Movement represents the accounting fact derived from the current semantic state of the source document and applicable Posting Context.

### 23.2 Validated

A generated Movement is validated according to the applicable Movement Validation rules and Register Posting Contract.

A Movement that fails required validation MUST NOT proceed to Register processing.

### 23.3 Accepted for Register Processing

A Movement is accepted for Register processing when it satisfies the applicable Register Posting Contract.

Acceptance confirms that the Movement satisfies the semantic requirements necessary for the Register to process it.

Acceptance does not imply physical persistence.

### 23.4 Required Persistent Accounting Result

Accepted Movements participate in establishing the persistent accounting result required by the Posting operation.

The concrete persistence and application mechanism is outside the Movement contract and is coordinated through the applicable Posting and Persistence Architecture boundaries.

The Movement contract therefore does not define separate normative lifecycle states such as Applied or Persisted.

Whether a Movement has contributed to the required persistent accounting result is determined by the overall Posting operation and its applicable consistency boundary.

### 23.5 Lifecycle Boundary

The Movement lifecycle MUST NOT be interpreted as an independent transaction or persistence lifecycle.

The authoritative Posting lifecycle remains:

```text
Posting Request
        ↓
Validate Posting Preconditions
        ↓
Resolve Posting Handler
        ↓
Create Posting Context
        ↓
Execute Posting Handler
        ↓
Generate MovementSet
        ↓
Validate MovementSet
        ↓
Coordinate Required Persistent Result
        ↓
Logical Completion
        ↓
Publish Posting Events
```

Movement semantics participate in this lifecycle but do not replace or extend it with a separate physical persistence lifecycle.

---

## 24. Unposting Semantics

Unposting removes the applicable accounting effects produced by a previously successful Posting operation.

The semantic relationship is:

```text
Posted Document
      ↓
Unposting
      ↓
Identify Applicable Accounting Effects
      ↓
Remove Accounting Effects
      ↓
Logical Completion
```

Unposting does not mean mutating the semantic meaning of an existing Movement into something else.

The accounting effects associated with the source document are explicitly removed or otherwise reversed according to the applicable Register architecture.

The exact mechanism is outside this step.

Unposting must preserve source document identity semantics so that the applicable accounting effects can be identified reliably.

---

## 25. Reposting Semantics

Reposting rebuilds the accounting result from the current semantic state of the source document.

The semantic lifecycle is:

```text
Already Posted Document
        ↓
Reposting Request
        ↓
Current Document State
        ↓
Generate New MovementSet
        ↓
Validate New MovementSet
        ↓
Establish New Persistent Accounting Result
        ↓
Logical Completion
```

Reposting does not rely on manually mutating existing Movements as its primary semantic mechanism.

Instead, Posting is re-evaluated from the current document state.

The exact replacement/removal strategy for previous accounting effects is deferred to the Reposting implementation step.

---

## 26. Reference and Identity Semantics

Movement values may contain references to domain objects or other architectural identities.

Such references must preserve the identity semantics established by the domain and persistence architectures.

A durable Movement must not depend on a transient runtime object reference.

Therefore:

```text
Reference
    ↓
Explicit domain/object identity
```

rather than:

```text
Reference
    ↓
Runtime Python object
```

This applies to:

* source document references;
* dimension values;
* resource references;
* attribute references;
* Register-related identities;
* other durable domain references.

The exact reference representation is outside the scope of this step.

---

## 27. Error Semantics

Movement-related failures are semantic failures of the Posting operation when they prevent the required accounting result from being established.

Examples include:

* missing required source identity;
* invalid Register identity;
* invalid movement type;
* missing required dimension;
* invalid dimension value;
* missing required resource;
* invalid resource value;
* missing required attribute;
* invalid reference;
* Register Posting Contract violation;
* inability to establish the required accepted accounting result.

The exact exception hierarchy and error codes are implementation/API concerns.

The semantic rule is:

> A Movement failure that prevents the required accounting result from being established must not be reported as successful Posting.

Errors must not be hidden through silent correction or data loss.

---

## 28. Consistency Boundary

Movements produced by one Posting operation may participate in multiple persistent effects.

Examples include:

```text
Movement persistence
Document posting state
Derived accounting state
Dependency state
Other required persistent effects
```

When those effects form part of one logical Posting result, they must participate in the applicable consistency boundary defined by Persistence Architecture.

Conceptually:

```text
Posting
    ↓
Complete MovementSet
    ↓
Required Persistent Effects
    ↓
Applicable Persistence Scope
    ↓
Logical Completion
```

This step does not prescribe:

* database transactions;
* begin/commit/rollback APIs;
* isolation levels;
* locking;
* distributed transactions;
* retry mechanisms.

Physical consistency mechanisms remain implementation-specific.
