# Phase 6 — Step 8 — Goods Receipt → Inventory

## 1. Purpose

This document defines the Standard Configuration contract for the first concrete Posting vertical slice:

```text
Goods Receipt
      ↓
Posting
      ↓
Posting Context
      ↓
Goods Receipt Posting Handler
      ↓
MovementSet
      ↓
Inventory Register Posting Contract
      ↓
Inventory Register
```

The scenario is: a successfully posted Goods Receipt establishes Inventory quantity accounting effects for the quantities received by the document.

This step applies the generic Posting, Movement, Register, consistency, and persistence boundaries established by previous Phase 6 and Phase 5 steps. It does not redefine those boundaries.

## 2. Relationship with Phase 6 Architecture

Step 8 depends on Steps 1–7 and MUST use their contracts without introducing a parallel Posting mechanism.

```text
Generic Phase 6 Posting Architecture
                ↓
      Standard Configuration
                ↓
     Goods Receipt Posting
                ↓
       Inventory Register
```

## 3. Standard Configuration Boundary

Platform owns Posting API, Posting Engine, Posting Context, handler infrastructure, movement validation, register-contract infrastructure, persistence/application coordination, and Posting result semantics.

Standard Configuration owns Goods Receipt posting semantics, its Posting Handler, Goods Receipt → Inventory mapping, Inventory posting configuration for this scenario, and document-specific posting validation.

Platform MUST NOT depend on Goods Receipt or Inventory implementation details.

## 4. Goods Receipt as Posting Source

Goods Receipt is the source document and uses the existing runtime representation `ObjectInstance`.

`ObjectInstance.identity` MUST be propagated as `Movement.source_document_identity`. Python object identity MUST NOT become durable accounting identity.

The Goods Receipt document remains the source of truth for accounting facts generated by its Handler.

## 5. Goods Receipt Posting Semantics

For this slice, a Goods Receipt represents receipt of inventory quantities.

Conceptually:

```text
Goods Receipt Line
    ↓
Product + Warehouse + Quantity
    ↓
Inventory Movement
```

A successful posting increases the applicable Inventory quantity fact for the specified product and warehouse context.

## 6. Posting Preconditions

At minimum:

* the supplied source `ObjectInstance` represents the Goods Receipt being posted;
* the document is postable according to the applicable Posting/document semantics;
* required Goods Receipt metadata is available;
* the Goods Receipt Handler can be resolved;
* every inventory-contributing line contains the required semantic data;
* the Inventory Register and its applicable posting contract are available.

The existence or loading of a persistent document is an application/runtime concern and MUST NOT be introduced as a separate Goods Receipt posting mechanism by this step.

Missing or invalid business data causes known Posting failure.
```

## 7. Goods Receipt Posting Handler

Conceptual contract:

```python
class GoodsReceiptPostingHandler(PostingHandler):
    def post(self, context: PostingContext) -> MovementSet:
        ...
```

The Handler may inspect the document and generate Inventory Movements.

It MUST NOT persist movements, access Storage Providers, control transactions, manage Persistence Scope, publish events, manage dependencies, or update unrelated totals.

The Handler owns document-specific accounting semantics only.

## 8. Goods Receipt Line Semantics

For the initial slice the minimum semantic information is:

```text
Product
Warehouse
Quantity
```

A line without sufficient information to construct a valid Inventory fact MUST fail explicitly. Missing values MUST NOT be silently inferred.

## 9. Product Dimension

Product identifies the inventory item affected by the Movement and is derived from the Goods Receipt line according to Standard Configuration metadata.

The Handler MUST NOT substitute an unrelated product or use uncontrolled runtime state.

## 10. Warehouse Dimension

Warehouse identifies the inventory location affected by the Movement.

Warehouse is required for this slice unless existing Inventory metadata explicitly defines an equivalent location dimension.

Missing required Warehouse information prevents successful Posting.

## 11. Inventory Quantity Resource

Quantity is the quantitative resource carried by the Inventory Movement.

```text
Dimensions:
    Product
    Warehouse

Resources:
    Quantity = received quantity
```

The concrete representation MUST follow the existing value/type architecture and Inventory Register Posting Contract. Exact numeric semantics MUST be preserved; floating-point representation MUST NOT be introduced where the existing domain/value architecture provides an exact representation.

## 12. Quantity Sign Semantics

Goods Receipt represents an Inventory increase.

The concrete sign convention MUST be defined by the Inventory Movement Type and resource semantics and used consistently across Posting, Register acceptance, persistence, and reads.

The semantic invariant is:

```text
Goods Receipt
    ↓
Inventory quantity increases
```

## 13. Inventory Register Identity

Every generated Movement MUST explicitly identify the Inventory Register.

```text
Goods Receipt
      ↓
Movement.register_identity
      ↓
Inventory Register
```

The Handler MUST NOT persist directly to Inventory storage.

```markdown
## 14. Movement Type

The Goods Receipt scenario requires one concrete Movement Type representing the Inventory receipt/increase semantic.

The universal Movement contract does not introduce a global Movement Type vocabulary.

The scenario-specific Movement Type MUST be explicitly selected as Standard Configuration before implementation of the Goods Receipt Handler and Inventory Register Contract.

The selected Movement Type MUST:

* have an explicit stable identity;
* be accepted by the Inventory Register Contract;
* represent the Goods Receipt Inventory-increase semantic;
* participate deterministically in Movement generation and validation.

An existing glossary or legacy vocabulary MUST NOT be adopted automatically merely because a similarly named value exists there.

The selected Movement Type is a prerequisite for implementation and MUST be recorded in the final Step 8 contract before implementation begins.
```


```markdown
## 15. Movement Time

The Step 8 implementation MUST explicitly determine whether Inventory accounting for Goods Receipt requires accounting time/date.

If accounting time/date is required, the Goods Receipt Handler MUST obtain it from the approved Posting Context time boundary or from an explicitly defined Goods Receipt field according to the selected accounting semantics.

The Handler MUST NOT call uncontrolled system time.

If Inventory accounting does not require temporal information for this vertical slice, the generated Movement MUST NOT introduce an incidental timestamp merely for persistence or implementation convenience.

Equivalent semantic inputs and equivalent relevant Posting Context inputs MUST produce equivalent movement semantics.

The selected temporal rule MUST be recorded in the final Step 8 contract before implementation begins.
```

## 16. Movement Generation

The Handler generates one complete MovementSet.

For the initial slice:

```text
one eligible Goods Receipt line
        →
one Inventory Movement
```

For `n` eligible inventory lines, the default result contains `n` movements.

No implicit aggregation or splitting is allowed without an explicit semantic rule.

## 17. Movement Ordering

Movement ordering MUST be deterministic whenever observable. It must derive from semantic document ordering rather than incidental set, dictionary, database, or provider ordering.

Where line order is semantically meaningful, generated movement order should preserve it.

## 18. MovementSet Completeness

The Handler MUST return the complete set of Inventory accounting effects required by the current Goods Receipt state before validation.

The Register MUST NOT infer missing movements from the document.

## 19. Inventory Register Posting Contract

For this slice the Inventory Register Contract MUST enforce at least:

* target Register is Inventory;
* configured Goods Receipt Movement Type;
* valid Product dimension;
* valid Warehouse dimension;
* Quantity resource present;
* required concrete Quantity type;
* applicable Quantity constraints.

Invalid movements MUST be rejected before they can contribute to the persistent accounting result.

The contract defines Inventory acceptance and must not contain unrelated Goods Receipt business logic.

## 20. Movement Validation

The generic validation boundary remains:

```text
Goods Receipt Handler
        ↓
MovementSet
        ↓
Movement Validation
        ↓
Inventory Register Contract
        ↓
Accepted MovementSet
```

Handler generates; validator validates; Register Contract defines Inventory acceptance; persistence/application coordination establishes the required persistent result.

## 21. Required Persistent Accounting Result

Successful Goods Receipt Posting requires establishment of the Required Persistent Accounting Result.

For this slice this includes the Inventory accounting effects represented by the MovementSet and the persistent state required by the applicable Posting/Register architecture.

The concrete database, storage, and physical transaction mechanism remain outside this document.

## 22. Post Flow

```text
Goods Receipt
      ↓
Public Posting API
      ↓
Posting Engine
      ↓
Validate Preconditions
      ↓
Resolve Goods Receipt Handler
      ↓
Create Posting Context
      ↓
Execute Handler
      ↓
Generate MovementSet
      ↓
Validate MovementSet
      ↓
Inventory Register Contract
      ↓
Coordinate Required Persistent Result
      ↓
Logical Completion
      ↓
DocumentPosted
      ↓
Success
```

Generating a MovementSet alone is not Posting success.

## 23. Failure Semantics

Known failures include invalid document state, missing posting data, Handler resolution failure, Handler validation failure, incomplete MovementSet, movement validation failure, Register Contract rejection, and known persistence/application failure.

If the persistent outcome cannot be reliably determined, the operation MUST return Indeterminate Outcome.

Event publication failure after Logical Completion MUST NOT be reinterpreted as failure to establish the Inventory result.

```markdown
## 24. Empty Goods Receipt

An empty Goods Receipt requires an explicit Standard Configuration semantic rule.

The rule MUST select exactly one of the following behaviors for this vertical slice:

* reject the document as not postable; or
* allow a zero-effect Posting that produces an empty MovementSet and establishes no Inventory quantity effect.

The selected behavior MUST be deterministic, compatible with the generic Posting semantic contract, and covered by tests.

Step 8 does not prescribe one of these behaviors at the universal Posting Architecture level.
```


## 25. Invalid Quantity

Quantity MUST satisfy Goods Receipt and Inventory constraints.

An invalid quantity MUST cause Posting failure before successful accounting completion. Invalid values MUST NOT be silently coerced.

## 26. Reposting Semantics

Reposting regenerates Inventory accounting effects from the current Goods Receipt state.

```text
Posted Goods Receipt
        ↓
Repost
        ↓
Current Document State
        ↓
New MovementSet
        ↓
Validate
        ↓
Establish New Inventory Result
        ↓
Logical Completion
        ↓
DocumentReposted
```

The Handler MUST NOT use existing persisted movements as the primary source of current accounting semantics.

Obsolete-effect removal/replacement is coordinated through the Posting Result Coordinator and persistence/application boundary.

## 27. Reposting Determinism

Equivalent Goods Receipt semantic state plus equivalent relevant Posting Context inputs MUST produce semantically equivalent Inventory movements.

Runtime object identity, storage provider, persistence layout, incidental collection order, uncontrolled time, and unrelated external state MUST NOT alter accounting meaning.

## 28. Unposting Boundary

Unposting removes the applicable Inventory effects established by the Goods Receipt Posting operation.

The Handler does not remove persisted movements. The Posting Engine coordinates removal through the established Result Coordinator boundary.

```text
Posted Goods Receipt
        ↓
Unpost
        ↓
Identify applicable effects
        ↓
Remove Inventory effects
        ↓
Logical Completion
        ↓
DocumentUnposted
```

## 29. Identity Semantics

Identity boundaries remain distinct:

```text
Goods Receipt ObjectInstance.identity
        ↓
Movement.source_document_identity

Inventory Register identity
        ↓
Movement.register_identity

Movement identity
        ↓
identity of accounting fact
```

Python object identity MUST NOT be persisted as an accounting identifier.

## 30. Phase 5 Boundary Preservation

Step 8 MUST use the existing Phase 5 architecture without reopening it.

In particular:

* `ObjectInstance` remains the runtime document representation;
* runtime and persistent representations remain distinct;
* durable state remains explicit;
* Persistence Scope remains a persistence/application boundary;
* Storage Provider remains behind its boundary;
* Posting does not depend on storage layout/provider details.

No Goods Receipt-specific persistence shortcut is permitted.

## 33. Testing Strategy

### Handler tests

Verify:

* one valid line → one Inventory Movement;
* multiple lines → expected MovementSet;
* source identity preservation;
* Product/Warehouse/Quantity mapping;
* Movement Type;
* deterministic ordering;
* explicit failure for invalid input.

### Register contract tests

Verify required Register identity, Movement Type, Product, Warehouse, Quantity, type constraints, and rejection of invalid data.

### Posting integration tests

Verify Handler resolution, Posting Context, MovementSet generation/validation, Inventory acceptance, Required Persistent Result, and success only after Logical Completion.

### Failure tests

Cover invalid document, missing Product/Warehouse, invalid Quantity, Handler resolution failure, movement validation failure, Register rejection, known persistence failure, Indeterminate outcome, and post-completion event publication failure.

### Reposting tests

Verify current document state is authoritative, obsolete effects are handled through the proper boundary, new movements are correct/deterministic, and failure is not reported as success.

## 34. Vertical Slice Test

The primary integration test must exercise:

```text
Goods Receipt
    ↓
Public Posting API
    ↓
Posting Engine
    ↓
Goods Receipt Posting Handler
    ↓
MovementSet
    ↓
Movement Validation
    ↓
Inventory Register Contract
    ↓
Required Persistent Accounting Result
    ↓
Inventory quantity fact
```

The test MUST verify the accounting fact at the Register boundary, not stop at Movement generation.

## 35. Inventory Quantity Acceptance

Conceptually:

```text
Before:
Inventory(Product, Warehouse) = Q

Goods Receipt:
Quantity = R

After successful Posting:
Inventory(Product, Warehouse) = Q + R
```

The concrete read/query mechanism is implementation-specific.

The semantic requirement is that successful Posting establishes the resulting Inventory quantity fact.

## 36. Failure Atomicity

Failure before Logical Completion MUST NOT expose a successful partial Inventory result.

Known persistence failure is known Failure.

Unknown persistent outcome is Indeterminate Outcome.

The vertical slice preserves Step 5 consistency semantics.

## 37. Event Boundary

`DocumentPosted`, `DocumentUnposted`, and `DocumentReposted` are published only after their respective Logical Completion.

Events do not establish Inventory effects.

## 38. Dependency Boundary

Goods Receipt posting may use dependency/restoration integration where required, but the Handler does not own the dependency graph.

Dependency effects forming part of the Required Persistent Accounting Result participate in the applicable consistency boundary.
